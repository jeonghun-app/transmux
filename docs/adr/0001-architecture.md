# ADR 0001 — RTSP→HLS 트랜스먹싱 파이프라인 아키텍처

- 상태: 채택 (PoC 검증 완료)
- 날짜: 2026-08-31
- 후속: [ADR 0003](0003-camera-solution.md), 2026-09-12

기본 수집·소유권 구조는 유지한다. 후속 구현은 영상 복사에 더해 선택적 AAC 음성
변환·fMP4와 별도 재생 서비스를 추가했다. 아래 코덱·전달의 미결 검토는 초기 설계
기록이며 현재 지원 범위는 [솔루션 가이드](../solution.md)를 따른다.

## 배경

Wowza Streaming Engine을 제거하고, IP 카메라의 RTSP(H.264/H.265)를
트랜스코딩 없이 HLS로 잘라 S3에 저장하는 경량 모듈을 자체 개발한다.
목표는 서버당 625채널, CPU 4~8코어, 메모리 8GB, 30일 이상 무중단이다.

## 결정

### 1. Go supervisor + 채널당 ffmpeg 서브프로세스

세 가지 후보를 검토했다.

| 방식 | 채택 여부 | 근거 |
|---|---|---|
| Go supervisor + 채널당 ffmpeg 프로세스 | **채택** | RTP 재조립, SPS/PPS/VPS, PTS/DTS wrap, PAT/PMT/PCR, continuity counter를 모두 검증된 코드가 처리한다. 채널 하나의 장애가 다른 채널로 전파되지 않는다. 실측 결과 자원 목표에도 거의 부합한다. |
| 단일 프로세스 libav 바인딩 (cgo) | 보류 | 메모리는 더 줄지만 native crash가 샤드 전체를 죽이고, FFmpeg ABI 고정과 io_open/io_close 콜백 연결이 필요하다. 실측으로 서브프로세스 방식이 목표에 근접함이 확인되었으므로 지금 투자할 이유가 없다. |
| 순수 Go 구현 (gortsplib + TS muxer 자작) | 거부 | H.264 FU-A/STAP-A, H.265 fragmentation/AP, IDR/CRA 판정, PCR, HEVC stream type을 직접 구현해야 한다. Wowza를 없애면서 유지보수 대상 미디어 엔진을 새로 만드는 결과가 된다. |

주의: `pion/rtsp`라는 패키지는 존재하지 않는다. Go RTSP 클라이언트의
실질적 선택지는 `bluenviron/gortsplib`이다. 순수 Go 방안을 재검토할
경우 이 사실을 전제로 해야 한다.

### 2. 세그먼트는 tmpfs 스풀 경유, stdout 파이프 분할은 사용하지 않음

ffmpeg의 HLS muxer가 tmpfs에 `.ts`와 로컬 `.m3u8`을 쓰고, Go가 이를
폴링해 업로드한다.

`ffmpeg ... -f hls ... -` 형태로 stdout에서 받아 Go가 자르는 방식은
채택하지 않았다. 연속 MPEG-TS 바이트 스트림은 임의 오프셋이나 188바이트
패킷 경계에서 자를 수 없다. 독립 재생 가능한 세그먼트를 만들려면 access
unit 경계 판정, random-access frame 판정, 세그먼트별 PAT/PMT 배치,
continuity counter, PCR, 정확한 EXTINF 계산을 모두 다시 구현해야 한다.
이는 "메모리 업로드 최적화"가 아니라 TS segmenter 자체 구현이다.
덧붙여 HLS muxer는 출력 파일이 여러 개이므로 단일 stdout으로 보낼 수
없다.

폴링을 쓰고 inotify를 쓰지 않은 이유: watch descriptor가 필요 없고,
이벤트 유실이 원리적으로 없으며, 재시작 후 잔여 파일 복구를 같은 코드가
겸한다.

### 3. 업로드 순서는 세그먼트 먼저, 매니페스트 나중

한 번의 스캔에서 완성된 세그먼트를 전부 PUT하고, 모두 성공한 뒤에만
매니페스트를 PUT한다. 세그먼트 PUT이 실패하면 매니페스트를 갱신하지 않고
스풀에 남겨 다음 tick에서 재시도한다.

매니페스트가 존재하지 않는 세그먼트를 참조하는 상태는 모든 시청자의
재생을 동시에 깨뜨린다. 반대로 저장은 되었으나 아직 목록에 없는
세그먼트는 보이지 않을 뿐 무해하다. 비대칭이므로 순서를 고정한다.

S3의 eventual consistency를 이유로 지연을 넣지 않는다. S3는 2020년 12월부터
신규 PUT과 덮어쓰기에 대해 strong read-after-write consistency를
제공한다. 실제 위험은 CDN/브라우저의 매니페스트 캐시이므로 매니페스트에는
`Cache-Control: no-cache, max-age=0`, 세그먼트에는 `immutable`을 붙인다.

### 4. 멀티파트 업로드 대신 PutObject

5초 세그먼트는 2~8Mbps에서 약 1.25~5MB다. 멀티파트의 마지막이 아닌 파트
최소 크기가 5MiB이므로 대부분 멀티파트를 쓸 수 없거나 파트가 하나뿐인
멀티파트가 된다. CreateMultipart/CompleteMultipart 왕복과 중단된 업로드
정리 비용만 늘어난다. 실측 세그먼트 크기는 1080p/4Mbps에서 약 2MB였다.

### 5. 재연결 감지는 Go 워치독, ffmpeg 소켓 타임아웃 옵션 아님

"N초 동안 새 세그먼트가 완성되지 않음"을 기준으로 Go가 ffmpeg을
종료한다. RTSP 소켓 타임아웃 옵션 이름(`-stimeout`, `-timeout`,
`-rw_timeout`)은 ffmpeg 릴리스마다 다르지만 이 판정은 모든 버전에서
동일하게 동작한다. 필요하면 `ffmpeg.input_args`로 버전별 옵션을 추가할 수
있다.

**중요한 구분**: 워치독은 "ffmpeg이 세그먼트를 만들어냈는가"(`Seen`)로
판정하고 "업로드가 성공했는가"(`Uploaded`)로 판정하지 않는다. 두 가지는
서로 다른 장애 도메인이다. S3 장애 중에 ffmpeg을 재시작하면 S3는 낫지
않으면서 스풀에 쌓인 세그먼트만 버린다. PoC 부하 시험에서 실제로 이
동작을 확인하고 수정했다.

### 6. 발행 시퀀스는 ffmpeg의 로컬 번호와 분리

ffmpeg은 재시작할 때마다 로컬 세그먼트 번호를 0부터 다시 매긴다. S3 객체
키에 이 번호를 쓰면 재연결 때마다 기존 객체를 덮어쓰고 플레이리스트가
과거로 되돌아간다. 따라서 채널별 monotonic 시퀀스를 별도로 유지하고
체크포인트에 저장한다. 재연결 후 첫 세그먼트에는
`EXT-X-DISCONTINUITY`를 붙이고, 윈도우에서 밀려난 discontinuity는
`EXT-X-DISCONTINUITY-SEQUENCE`에 반영한다.

### 7. 매니페스트는 Go가 직접 렌더링

ffmpeg의 로컬 플레이리스트는 "어떤 세그먼트가 완성되었고 실제 길이가
얼마인가"의 출처로만 쓰고, 발행되는 플레이리스트는 Go가 만든다. 그래야
객체 키, 시퀀스, discontinuity, 그리고 업로드 성공 여부를 매니페스트
내용과 일치시킬 수 있다.

`EXT-X-TARGETDURATION`은 설정값이 아니라 실제 EXTINF 최댓값의 올림값을
쓴다. GOP가 긴 카메라는 목표보다 긴 세그먼트를 내놓으며, 이때 target을
설정값으로 적으면 엄격한 플레이어가 멈춘다.

### 8. 세그먼트 길이는 카메라 GOP가 지배한다 (실측 확인)

트랜스코딩을 하지 않으므로 ffmpeg은 새 IDR을 만들 수 없다. `-hls_time`은
목표이자 하한이며, 실제 절단은 그 시점 이후 처음 오는 random-access
frame에서 일어난다.

실측(`internal/ffmpeg/ffmpeg_integration_test.go`, ffmpeg 6.1.2):

| 소스 GOP | `-hls_time` | 실제 세그먼트 |
|---|---|---|
| 2초 | 2초 | 2.000초 |
| 6초 | 2초 | **6.000초** |
| 8초 (라이브 RTSP) | 4초 | **8.000초** |

`split_by_time`은 쓰지 않는다. 비키프레임에서 자르면 세그먼트가 독립
재생되지 않는다.

따라서 **"세그먼트 4~6초"는 이 모듈이 보장할 수 있는 항목이 아니라
카메라 설정 계약**이다. 카메라의 IDR 간격을 목표 세그먼트 길이 이하
(권장 2~5초)로 맞춰야 한다. 누락 알람 임계값에 `max_gop_slack`을 둔
이유도 이것이다.

### 9. H.264는 MPEG-TS, H.265는 fMP4 권장

HEVC를 MPEG-TS로 운반하는 것은 stream type 0x24로 표준화되어 있어 생성
자체는 가능하다. 그러나 Apple의 HLS Authoring Specification은 HEVC를
fMP4로 담도록 요구하며, 범용 웹 플레이어(hls.js + MSE)에서 HEVC-in-TS의
동작은 OS/브라우저/하드웨어 디코더에 크게 좌우된다.

"생성 가능"과 "플레이어 호환"은 다른 문제다. 요구사항이 `.ts`를 명시하고
있으나, HEVC 카메라가 실제로 존재한다면 다음 중 하나를 선택해야 한다.

1. H.264는 `.ts`, H.265는 fMP4(`init.mp4` + `.m4s` + `EXT-X-MAP`)
2. HEVC도 `.ts`로 강제하되, 인증된 플레이어/디바이스 목록에서만 재생을
   보장한다고 요구사항에 명시

현재 구현은 `.ts`만 생성한다. fMP4 프로파일은 별도 command builder로
추가할 자리를 남겨두었다. 실제 카메라 코덱 분포를 먼저 조사할 것을
권한다.

### 10. 샤딩: 컨테이너당 50~75채널

625채널을 한 프로세스에 넣지 않는다. supervisor 재시작이나 배포가
625채널을 동시에 끊고, 재연결 폭주가 한 곳에 집중되고, 롤링 업데이트가
불가능해진다. 컨테이너당 50~75채널이면 625채널은 9~13개 샤드가 된다.

한 카메라를 두 샤드가 동시에 수신하면 같은 매니페스트 객체를 두 writer가
덮어써 플레이리스트가 두 타임라인 사이를 오간다. 따라서 카메라 할당은
active/active가 아니어야 한다.

**해결됨 (2026-09).** 이 ADR은 원래 lease에 DynamoDB 같은 외부 저장소가 필요할
것으로 보았다. 그 가정은 더 이상 유효하지 않다. S3와 MinIO 모두 `PutObject`에
`If-None-Match`(조건부 생성)와 `If-Match`(compare-and-swap)를 지원하며, 고정된
SDK·MinIO 버전에서 실측 확인했다. 따라서 새 의존성 없이 이미 쓰는 오브젝트
스토어만으로 소유권을 강제한다.

핵심은 lease 자체가 fence가 아니라는 점이다. lease를 획득해도 얼어붙은 이전
소유자가 들고 있는 유효한 CAS 토큰을 회수할 수는 없다. 그래서 새 소유자는
ffmpeg을 켜기 전에 방금 읽은 버전을 조건으로 매니페스트를 다시 써서 그 토큰을
소멸시킨다. 소유권 이전 시점은 lease 획득이 아니라 이 fence 쓰기다. 세부는
README "다중 호스트 소유권", 구현은 `internal/channel/lease.go`와
`Worker.fenceManifest`.

`Manager`는 여전히 프로세스 내 유일성을 보장하며, lease는 그 위에 프로세스 간
유일성을 얹는다.

### 11. 의존성은 AWS SDK만

Prometheus 클라이언트, YAML 파서, fsnotify를 모두 쓰지 않았다. 30일 이상
무중단 운영과 컨테이너 이미지 최소화가 목표이므로 공급망 표면을 줄이는
편이 낫다고 판단했다. 메트릭은 Prometheus 텍스트 형식을 직접 생성하고,
설정은 `encoding/json`, 스풀 감시는 폴링을 쓴다.

## 결과

- 검증된 미디어 처리 경로를 재구현하지 않는다.
- 채널 장애가 격리된다.
- 실측 기준 CPU 목표는 충족하고, 메모리 목표는 8GB에서 약 8.6GiB로
  초과한다. `docs/capacity-model.md` 참고.
- 오디오는 현재 제외(`-an`)되어 있다. 카메라 오디오 코덱 정책이 정해지면
  추가해야 한다.

## 미결 사항

1. 실제 카메라의 코덱/비트레이트/GOP 분포 조사
2. H.265 카메라 존재 여부와, 존재할 경우 fMP4 프로파일 구현
3. 오디오 요구사항 확정
4. 카메라 provider의 실제 DB/API 연동 (현재 static과 http 스켈레톤)
5. S3 lifecycle 정책 — 보존 기간이 정해지지 않으면 하루 수천만 객체가
   무한 축적된다
