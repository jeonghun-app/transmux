# 용량 모델 — 실측 기반

이 문서의 수치는 추정이 아니라 이 저장소의 PoC 스택에서 측정한 값이다.
측정 환경과 한계를 먼저 밝히고, 그 다음 625채널 목표에 대한 판정을 적는다.

## 측정 환경

- 호스트: Linux, 32 vCPU, 61GiB RAM
- 컨테이너: `transmux:latest` (Alpine 3.20 + ffmpeg 6.1.1, tini PID 1)
- 소스: MediaMTX 1.9.3, ffmpeg으로 생성한 합성 H.264 스트림
- 스풀: tmpfs
- 오브젝트 스토어: MinIO (동일 호스트)
- 측정 도구: `scripts/measure-capacity.sh`
- 측정값: 컨테이너 cgroup 메모리(`docker stats`), 즉 컨테이너 메모리
  리밋이 실제로 적용되는 값

### 이 측정의 한계 (반드시 감안할 것)

1. 모든 채널이 **동일한 MediaMTX 경로**를 구독한다. 먹서, 프로세스, 업로드
   비용은 정확하지만, 실제 카메라 625대가 각자 가져오는 TCP 세션, 지터,
   비트레이트 변동, 패킷 손실은 과소평가한다. **하한값으로 취급할 것.**
2. MinIO가 같은 호스트에 있어 S3 왕복 지연이 실제보다 짧다. 업로드 대기
   큐와 재시도 부하가 과소평가된다.
3. 합성 소스라 장면 변화가 없어 비트레이트가 매우 안정적이다.
4. 최대 50채널까지만 측정했다. 625채널은 선형 외삽이다.
5. 오디오가 없다(`-an`).

측정은 아래 별도 절을 참고할 것.

### 핵심 관찰

**1. 채널당 증분 메모리는 약 13.4~14.3 MiB이며 비트레이트에 무관하다.**

| 프로파일 | 채널당 증분 메모리 |
|---|---:|
| 704×480 0.5Mbps | 13.44 MiB |
| 1080p 4Mbps | 13.93 MiB |
| 640×360 1.5Mbps | 13.5~14.8 MiB |

비트레이트를 8배 바꿔도 채널당 메모리는 사실상 같다. **이것이 중요한 이유:
해상도를 낮추면 CPU·네트워크·저장량은 줄지만 메모리 목표는 개선되지 않는다.**
625채널 × 13.44 MiB = 8.20 GiB이므로 최저 비트레이트에서도 8GB 목표를 넘긴다.
메모리의 레버는 해상도가 아니라 예산 상향 또는 libav 멀티채널 worker다.

360p/1.5Mbps에서 13.5~14.8 MiB, 1080p/4Mbps에서 13.9 MiB. 비트레이트를
2.7배 올려도 채널당 메모리는 사실상 같다. 원인은 비용이 세그먼트 페이로드가
아니라 ffmpeg 프로세스의 고정 힙·스택·프로토콜 버퍼에서 나오기 때문이다.
업로더가 저장 즉시 로컬 세그먼트를 삭제하므로 스풀이 메모리를 잡지 않는다.

**2. 프로세스별 RSS를 더하면 크게 과대평가된다.**

2채널 실행 시 `ps` RSS는 ffmpeg 43MB + 42MB + Go 15MB = 약 100MB였으나,
실제 cgroup 사용량은 **39.15 MiB**였다. 모든 ffmpeg이 같은
libavcodec/libavformat 텍스트 페이지를 공유하기 때문이다. 용량 산정은
반드시 cgroup 값이나 PSS로 해야 하며 RSS 합계로 하면 안 된다.

**3. 스풀은 사실상 비어 있다.**

50채널에서 200KB. 업로더가 PUT 성공 직후 파일을 지우므로 정상 상태에서는
채널당 4KB 수준이다. tmpfs를 `local_list_size × 비트레이트 × 채널`로 잡을
필요가 없다. 다만 S3 장애 시에는 ffmpeg의 `delete_segments`가 반환할 때까지
`local_list_size` 개까지 쌓일 수 있으므로 그 최댓값으로 사이징해야 한다.

장애 시 실측: 1.5Mbps 채널 하나에서 오브젝트 스토어를 35초 끊었을 때 스풀이
9파일 7.0MB까지 찼다(`local_list_size` 10, GOP 2초). 즉 최악값은 대략
`local_list_size × 세그먼트 길이 × 비트레이트`이고, 4Mbps·625채널이면 약
`10 × 4초 × 4Mbps ≈ 20MB/채널`로 tmpfs 12GB가 필요해진다 — 8GB 컨테이너에서는
현실적으로 `local_list_size`를 줄이거나 채널 수를 낮춰야 한다. 운영 중에는
`transmux_channel_spool_bytes`와 `transmux_channel_spool_oldest_seconds`를 합산해
실제 헤드룸을 보면 된다.

**4. FD는 채널당 약 7.5개.**

50채널에서 373개. 625채널이면 약 4,700개다. 기본 `nofile=1024`로는 부족하니
컨테이너에 65535를 설정해야 한다(`deploy/docker-compose.poc.yml`의 `ulimits`
참고. 프로덕션 오케스트레이터의 task/pod 정의에도 같은 값을 넣어야 하며, 이
리포지토리에는 오케스트레이터 매니페스트가 포함되어 있지 않다).

**5. 프로세스는 채널당 1개 + 고정 5개.**

625채널이면 약 630 PID. ECS/EKS의 PID 리밋을 2000 이상으로 두어야 한다.

## CPU 정밀 측정

`docker stats`는 짧은 롤링 샘플을 소수점 둘째 자리까지만 보여주므로 채널당 약
0.5% 수준에서는 대부분 노이즈다. `scripts/measure-cpu.sh`는 컨테이너의 cgroup v2
`cpu.stat` `usage_usec` 카운터 증분을 실제 경과 시간으로 나눈다. 이것은 소비된
CPU 시간 그 자체다. 워밍업 45초, 측정 창 60초.

`d1`·`hd720`·`hd` 프로파일은 `make poc-up-capacity`로 해당 소스를 띄워야 한다.
`deploy/mediamtx.yml`에 경로만 선언돼 있어도 publisher가 없으면 RTSP는 오류 없이
무음을 흘리므로, 스크립트가 측정 전에 스트림을 프로브해 거부한다. 1채널 재측정
검증값: `--profile hd` 1채널에서 0.82% 코어로, 아래 표의 0.827%와 일치한다.

### 결과

| 프로파일 | 1채널 단독 | **마진/채널** | 625채널 | CPU ms/세그먼트 |
|---|---:|---:|---:|---:|
| **704×480 0.5Mbps GOP 2초** | 0.46% 코어 | **0.374% 코어** | **2.34 코어** | 15 ms |
| **1280×720 1Mbps GOP 2초** | 0.55% 코어 | **0.479% 코어** | **3.00 코어** | 19 ms |
| 640×360 1.5Mbps GOP 2초 | 0.64% 코어 | **0.577% 코어** | **3.61 코어** | 24 ms |
| 1920×1080 4Mbps GOP 4초 | 0.78% 코어 | **0.827% 코어** | **5.17 코어** | 31 ms |
| 640×360 1.5Mbps GOP 8초 | 0.59% 코어 | **0.534% 코어** | **3.34 코어** | 42 ms |

네 개의 비트레이트를 실측했으므로 보간식은 더 이상 필요하지 않다. 이전 문서의
2점 외삽식(`0.427 + 0.1 × Mbps`)은 **저비트레이트 구간을 21~28% 과대평가**했다
(0.5Mbps 예측 0.477% vs 실측 0.374%). 관계는 완전한 직선이 아니라 저비트레이트
쪽에서 약간 sublinear하다. 측정 범위(0.5~4Mbps) 안에서만 보간할 것.

프로세스별 분해(고채널 구간): **ffmpeg 81~84%, Go supervisor 16~19%.**
user/system 비율은 약 62:38이다. 트랜스코딩이 없으므로 디코드 연산이 아니라
syscall과 네트워크 I/O가 비용의 큰 부분을 차지한다.

컨테이너 고정 오버헤드(Go 런타임, GC, HTTP 서버)는 0.005 코어 수준으로 무시할 수
있다. 즉 **1채널 단독 비용과 마진 비용이 거의 같다.**

비트레이트 민감도: 메모리와 달리 CPU는 비트레이트에 반응한다. 1.5Mbps → 4Mbps에서
채널당 CPU가 43% 늘어난다(0.577% → 0.827%). TS 패킷 수와 옮겨야 할 바이트가
늘기 때문이다.

### 두 가지 중요한 관찰

**1. 선형으로 확장되며, 채널 수가 늘어도 채널당 비용이 나빠지지 않는다.**

| 프로파일 | 저채널 기울기 | 고채널 기울기 | 판정 |
|---|---:|---:|---|
| 360p GOP 2초 | 0.00606 | 0.00543 (75채널까지) | 선형, 오히려 감소 |
| 1080p GOP 4초 | 0.00761 | 0.00830 (50채널까지) | 선형 |
| 360p GOP 8초 | 0.00558 | 0.00511 (50채널까지) | 선형, 오히려 감소 |

"프로세스 수백 개면 컨텍스트 스위칭으로 성능이 급락한다"는 흔한 주장은 이
워크로드에서 관측되지 않았다. 각 ffmpeg이 대부분의 시간을 소켓 대기로 보내고
세그먼트 경계에서만 의미 있는 작업을 하기 때문이다. 다만 검증 범위는 75채널까지이며
625채널의 선형성은 여전히 외삽이다.

**2. GOP가 길면 초당 CPU는 줄고 세그먼트당 CPU는 늘어난다.**

GOP 8초는 GOP 2초보다 채널당 CPU가 7% 낮지만(0.534% vs 0.577%), 세그먼트 하나당
CPU는 75% 높다(42ms vs 24ms). 세그먼트 경계 작업(파일 닫기, 플레이리스트 갱신,
업로드, PUT)이 세그먼트당 고정 비용이기 때문이다.

**지연과 CPU가 상충한다.** ADR 0002 §5대로 지연을 줄이려면 GOP와
`target_duration`을 2초로 내려야 하는데, 그러면 세그먼트 수가 늘어 CPU와 S3 PUT
요청 수가 함께 오른다. 4초 → 2초는 PUT을 2배로 만든다.

### 측정 방법의 타당성 검증

모든 채널이 동일한 MediaMTX 경로를 구독하는 것이 결과를 왜곡하는지 확인했다.
독립 publisher 8개를 띄워 채널마다 별도 RTSP 세션을 갖게 하고 비교했다.

| 구성 | 채널당 CPU |
|---|---:|
| 8채널이 한 소스를 공유 | 0.617% 코어 |
| 8채널이 각자 독립 소스 | 0.606% 코어 |

차이가 노이즈 수준이다. 채널마다 자기 TCP 연결을 열고 RTP 역다중화·TS 먹싱·업로드를
각자 수행하므로 원본 스트림 공유 여부는 채널당 비용에 영향을 주지 않는다.
**따라서 공유 소스 기반 측정치를 그대로 신뢰할 수 있다.**

### 여전히 측정되지 않은 것

실제 카메라에서만 나타나며, 모두 CPU를 **올리는** 방향이다.

- 패킷 손실과 TCP 재전송
- 네트워크 지터
- 장면 변화에 따른 가변 비트레이트 (합성 소스는 거의 일정하다)
- 카메라별 RTSP keepalive와 세션 재협상
- **실제 S3 리전 엔드포인트의 TLS** — 현재 MinIO는 같은 호스트이고 평문이다.
  HTTPS 핸드셰이크와 왕복 지연은 supervisor 측 CPU와 업로드 큐 깊이를 함께 늘린다.
  세 항목 중 가장 클 가능성이 있다.

### 미구현 기능이 이 수치를 바꾸는가

| 남은 작업 | 채널당 CPU 영향 |
|---|---|
| 전달 경로 (CloudFront, playback API) | **없음.** 별도 서비스이며 egress는 S3/CDN이 처리 |
| VOD indexer | **없음.** 별도 서비스 |
| 샤드 lease | **구현됨.** CPU·메모리는 무시 가능하지만 `lease.renew_interval`마다 채널당 작은 PUT 하나가 추가된다(5초 주기·625채널 ≈ 125 PUT/s) |
| H.265 | 거의 없음. 여전히 `-c:v copy`이며 디코드하지 않는다 |
| 오디오 패스스루 | 소폭 증가. 먹싱할 스트림이 하나 늘고 TS 패킷이 증가 |
| 듀얼 스트림(서브스트림) | **채널당 비용은 그대로이나 채널 수가 2배.** 1,280 × 0.827% ≈ 10.6 코어로 4~8코어 예산을 넘긴다 |

즉 **측정을 위해 전체 구현을 기다릴 필요는 없다.** 남은 기능은 대부분 다른
프로세스에서 돌거나 영향이 미미하다. 수치를 실제로 움직이는 변수는 (a) 실제
카메라, (b) 실제 S3 TLS, (c) 듀얼 스트림 채택 여부다.

## 625채널 외삽과 판정

채널당 14 MiB, 1080p/4Mbps 기준 채널당 0.827% 코어로 외삽한다.

| 항목 | 625채널 추정 | 요구사항 | 판정 |
|---|---|---|---|
| 메모리 | 625 × 14 MiB + 25 MiB ≈ **8.6 GiB** | 8 GB 이내 | **초과** |
| CPU (1080p/4Mbps) | 625 × 0.827% ≈ **5.2 코어** | 4~8 코어 | **충족** |
| CPU (360p/1.5Mbps) | 625 × 0.577% ≈ **3.6 코어** | 4~8 코어 | **충족** |
| FD | ≈ 4,700 | — | `nofile=65535` 필요 |
| PID | ≈ 630 | — | PID 리밋 2000 이상 |
| 입력 대역폭 | 625 × 4Mbps = **2.5 Gbps** | — | 명시 없음, 확인 필요 |
| 출력 대역폭(S3) | **2.5 Gbps** | — | 명시 없음, 확인 필요 |
| S3 PUT (5초 세그먼트) | 125 세그먼트/s + 125 매니페스트/s + 125 lease 갱신/s(5초 주기) = **375 PUT/s** | — | 버킷 한도 3,500 PUT/s 대비 여유 |

### 결론

- **CPU 4~8코어는 달성 가능하다.** 1080p/4Mbps에서 약 5.2코어, 저비트레이트에서
  약 3.6코어다. 트랜스코딩이 없다는 점이 그대로 반영된 결과이며, 채널 수에 대해
  선형으로 확장되는 것도 확인했다.
- **메모리 8GB는 달성할 수 없다.** 정상 상태만으로 약 8.6GiB이고, 여기에는
  S3 지연 시의 업로드 큐, Go GC 헤드룸, 재연결 폭주 시의 여유가 전혀 없다.

권고는 둘 중 하나다.

1. **메모리 요구사항을 625채널당 12GiB로 조정한다.** (권장) 8.6GiB 정상
   상태에 약 40% 헤드룸을 둔 값이다.
2. **8GiB를 고정 제약으로 유지하고 서버당 채널 수를 약 500으로 낮춘다.**
   500 × 14 MiB ≈ 7.0GiB로 헤드룸이 확보된다. 640대 롤아웃 계획은
   서버 수 재산정이 필요하다.

메모리를 더 줄여야 한다면 다음 순서로 검토한다.

1. `local_list_size`를 낮춘다 — 스풀은 이미 작아서 효과는 제한적이다.
2. 채널 25~50개를 한 프로세스에서 처리하는 libav worker로 전환한다.
   프로세스별 중복 힙·버퍼가 제거되므로 채널당 14 MiB의 상당 부분이
   사라진다. ADR 0001에서 보류한 항목이며, 여기서 비용이 정당화된다.

## 샤딩 권고

| 컨테이너당 채널 | 컨테이너 메모리 | 컨테이너 CPU | 625채널 필요 샤드 |
|---:|---:|---:|---:|
| 50 | 0.75 GiB + 헤드룸 → **1.5 GiB** | 0.5 코어 → **1 vCPU** | 13 |
| 75 | 1.1 GiB + 헤드룸 → **2 GiB** | 0.7 코어 → **1 vCPU** | 9 |

50채널로 시작해 실카메라로 재측정한 뒤 75까지 올리는 것을 권한다.
컨테이너 하나가 죽어도 영향은 8%(50채널) 또는 12%(75채널)에 그친다.

## S3 비용 (요청 요금만)

5초 세그먼트, 625채널, 매 세그먼트마다 매니페스트 갱신 기준.

- 세그먼트 PUT: 125/s → 10,800,000/일
- 매니페스트 PUT: 125/s → 10,800,000/일
- 합계: **21,600,000 PUT/일**
- $0.005/1,000 PUT 가정 시 약 **$108/일, $3,240/30일**

세그먼트 2개마다 매니페스트를 갱신하면 매니페스트 PUT이 절반이 되고
발행 지연은 최대 한 세그먼트 늘어난다. 현재 구현은 매 세그먼트 갱신이며,
드레인 한 번에 여러 세그먼트를 처리한 경우에는 매니페스트를 한 번만
올리므로 밀렸다가 따라잡을 때는 자동으로 절약된다.

**저장 용량이 요청 요금보다 훨씬 크다.** 625채널 × 4Mbps는 원본 데이터만
약 27TB/일이다. **보존 기간과 S3 lifecycle 정책이 요구사항에 반드시
추가되어야 한다.** 현재 요구사항에는 없다.

정확한 요금은 리전, 복제, 암호화, GET, CDN 설정에 따라 달라진다.
AWS Pricing Calculator로 확인할 것.

## 재측정이 필요한 시점

이 문서의 수치는 합성 소스 기준이다. 다음 단계에서 반드시 다시 측정한다.

1. 실제 카메라 3종 이상, 각자 다른 제조사·비트레이트·GOP
2. 100 → 250 → 625채널 단계적 증가
3. 24시간 부하 후 cgroup 메모리가 평탄해지는지 (누수 판정)
4. 30일 soak에서 메모리 증가 기울기가 0에 가까운지
5. S3를 실제 리전 엔드포인트로 두었을 때의 PUT p95/p99와 업로드 큐 깊이
