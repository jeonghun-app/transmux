# Wowza 대체 범위

이 프로젝트의 대상은 **고정 IP 카메라의 RTSP 수집, 라이브 관제,
녹화 검색·재생과 MP4 추출**이다. 이 경로는 `transmuxd`와 `playbackd`,
비공개 S3 및 포함된 운영자 화면으로 구현했다.

Wowza 제품의 모든 방송 프로토콜과 확장 기능을 복제하는 범위는 아니다.
아래 판정은 현재 리포지토리의 구현·검증 결과이며 특정 Wowza 버전의
제품 사양이나 고객이 실제 사용하는 기능 목록을 대신하지 않는다.

## 구현과 검증

| 관제 업무 | 현재 구현 | 검증·조건 |
|---|---|---|
| RTSP/TCP 수집 | 채널별 ffmpeg, 자동 재연결·실패 격리 | 합성 RTSP 및 저장소 장애 검증 |
| 영상 복사 | H.264·H.265 `-c:v copy` | 실제 H.264 TS/fMP4, H.265 fMP4 디코딩 |
| 카메라 음성 | 제외, 복사, AAC 변환 | AAC 복사·G.711 μ-law→AAC 검증 |
| HLS 패키징 | MPEG-TS·fMP4, 실제 duration·PDT·초기화 파일 | 2초·8초 GOP, 날짜·재시작, 명시적 HEVC 설정의 hvc1 표시 |
| 라이브 전달 | 비공개 S3를 읽는 인증 프록시 | 매니페스트·미디어·초기화·HEAD·Range 인증 |
| 시청자 권한 | 센터·카메라별 live/recording/export/manage | 잘못된 서명·audience·만료·범위 거절 |
| 다중 카메라 화면 | 1·4·9·16분할, 선택·닫기·오류·재연결 | 실제 브라우저 검증 항목은 솔루션 검증 기록 참조 |
| 녹화 검색 | 영속 시각 인덱스, 단절 기간·복구 상태 | 자정 경계, 재시작, 늦은 객체·커서 복구 |
| 과거 구간 재생 | 고정 VOD 목록·ENDLIST·세션 갱신 | 늦은 인덱싱에도 발급된 목록 유지 |
| MP4 추출 | 제한된 비동기 remux, 취소·다운로드 | 세 코덱 조합의 MP4 영상·음성 디코딩 |
| 카메라 관리 | 추가·편집·비활성화, ETag 충돌 검사 | 공유 목록 조건부 쓰기, 실제 수집 반영 |
| 서버 배정 | `shard_id`·서버별 한도·공유 원장 | 필터·배정 이동 테스트, lease 중복 소유 방지 |
| 장애 인수 | lease + 매니페스트 fence, 시퀀스 복구 | 중복 실행·동결 소유자 인수·과거 writer 차단 |
| 보존 관리 | 보수적 날짜 정리·읽기 전용 미리 보기 | 기존·미색인 미디어 정리, 제어 객체 제외 |
| 대규모 보존 | 선택적 미디어 태그·S3 Lifecycle 예시 | 실제 기간·접두사·처리율은 운영 설정 |
| 상태 감시 | 내부 health·Prometheus, 수집/저장 장애 구분 | 인증 사용자 API와 내부 모니터링 분리 |

구체적인 API·제한·IAM 계약은 [솔루션 가이드](solution.md),
검증 기록은 [수집 품질 점검](quality-review.md)과
[솔루션 검증](solution-review.md)에 있다.

## 지원하지 않거나 별도 연동이 필요한 범위

| 항목 | 현재 상태·영향 |
|---|---|
| WebRTC, LL-HLS, RTMP/SRT, RTSP push·egress | 구현하지 않음. 기존 고객이 이 프로토콜을 사용하면 별도 경로가 필요 |
| 1∼3초 지연 | 일반 HLS·카메라 GOP에 의해 제한. 기존 지연 요구를 충족하는지 현장에서 측정 필요 |
| ABR·다중 해상도·영상 트랜스코딩 | 단일 영상 복사 프로파일. main/sub 자동 전환·온디맨드 수집 없음 |
| DASH·DRM·HLS 암호화·워터마크 | 구현하지 않음 |
| HTTPS·외부 SSO·CDN | 운영 프록시·인증 어댑터·CDN 구성이 필요. HS256 중앙 발급 계약 제공 |
| 즉시 개별 토큰 폐기·MFA | 구현하지 않음. 기존 권한은 토큰 만료 또는 키 교체까지 유효 |
| 재생 서버 HA | 단일 playbackd·영속 bbolt 기준. 공유 세션·내보내기·DB 장애 전환 없음 |
| 모든 HEVC 브라우저 | OS·브라우저 디코더 의존. ffmpeg 검증이 모든 단말 지원을 의미하지 않음 |
| RTSPS·실제 카메라 전체 모델 | URL은 허용하지만 장비별 TLS·음성·타임스탬프 호환 실검증 필요 |
| 프레임 단위 증적 절단 | 조각 경계 remux. 정확한 프레임·법적 증적 서명 기능 없음 |
| 한 VOD 안의 TS/fMP4 형식 전환 | 형식별로 구간을 나눠 요청 |
| ONVIF 탐색·PTZ·양방향 음성·알람 메타데이터 | 구현하지 않음. VMS 또는 장비 연동 계층의 영역 |
| 자동 A/B RTSP 소스 전환 | 같은 소스 재연결은 지원, 대체 소스 선택은 없음 |
| 수백 채널 장기 운영 보장 | 현재 검증 범위를 넘음. 실제 채널·시청·인덱스·저장 규모 측정 필요 |

## 기존 Wowza에서 전환하는 순서

1. 기존 서비스가 쓰는 입력·출력 프로토콜, 단말, 허용 지연, 카메라 음성·코덱을
   이 표와 대조한다. RTSP 수집·HLS 관제 경로를 전환 단위로 잡는다.
2. 실제 카메라 일부로 별도 저장 prefix에 병행 수집한다. 기존 서비스와 동일한
   S3 객체 키에 두 writer를 연결하지 않는다.
3. 실제 계정·센터·카메라 범위를 연동하고 허용·거절 계정 모두로 확인한다.
   S3 비공개, HTTPS, URL 로그 마스킹을 포함해 재생 경로를 점검한다.
4. 라이브 지연·음성·긴 GOP·네트워크 단절·녹화 구간·MP4를 실제 단말에서 비교한다.
   기준을 만족한 센터부터 클라이언트의 재생 API를 전환한다.
5. 목표 채널 수와 동시 시청량으로 CPU·메모리·네트워크·인덱스 디스크·복구 시간과
   보존 처리율을 측정한다. 이전 무음 수집 경로의 외삽을 전체 솔루션 용량으로
   사용하지 않는다.
6. 기존 녹화 조회 경로를 보존한 상태에서 소스 연결과 시청자를 단계적으로 옮긴다.
   기존 Wowza 녹화의 메타데이터 변환·일괄 이관기는 이 구현에 포함하지 않는다.
   전환 실패 시 기존 재생 API로 되돌릴 수 있게 유지한다.

수집기의 롤링 교체는 시퀀스·키 재사용을 막지만 미디어 공백 0초를 보장하지 않는다.
lease 만료·획득과 카메라 다음 키프레임까지의 시간이 장애 복구 예산에 들어간다.

기존 [용량 모델](capacity-model.md)은 최대 75채널 실측으로 625채널 수집 메모리를
약 8.6GiB로 외삽했다. 목표 8GB에 이미 여유가 없고, 새 오디오 변환·재생·인덱싱
부하는 별도다. 수집 서버를 나누거나 메모리를 늘리는 배치를 실제 부하로 확정해야 한다.
